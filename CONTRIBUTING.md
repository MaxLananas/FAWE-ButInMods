# Contributing to FAWE-BIM

Thanks for taking the time to help. This document explains how the project is built, how a command
is ported, and what a change is expected to look like.

## Ground rules

* **English only.** Sources, identifiers, comments, documentation, command descriptions, error
  messages and commit messages are all in English.
* **Behaviour follows upstream.** WorldEdit 7.3.17 and FastAsyncWorldEdit are the compatibility
  target: command names, aliases, flags, argument order, parser ids, messages and default values.
  When the two disagree, FAWE wins, because FAWE is the superset this mod reproduces.
* **No placeholder implementations.** A command either does the work or is not registered. Large
  features are split into reviewable steps, and unfinished commands stay in `docs/STATUS.md`.
* **Comments explain decisions, not code.** Write a comment when a reader would otherwise ask "why
  is it done this way?" — parser quirks, upstream behaviour that looks wrong but is intentional,
  chunk/index layouts. Do not narrate what the next line does, do not add banner comments, do not
  leave commented-out code behind.

## Setting up

```bash
git clone https://github.com/MaxLananas/FAWE-BIM
cd FAWE-BIM
./gradlew build
```

JDK 21 is the only prerequisite; Gradle, Loom, Minecraft, the Parchment mappings and Fabric API are
downloaded by the build.

Useful commands:

| Command | What it does |
|---|---|
| `./gradlew :core:selfTest` | runs the engine test suite (`SelfTestMain`) without Minecraft |
| `./gradlew :core:genDocs` | regenerates `docs/COMMANDS.md`, `docs/commands-spec.json`, `docs/STATUS.md` from the live registry |
| `./gradlew :core:verify` | runs the self-tests and checks every inventory name against the dispatcher |
| `./gradlew :fabric:runServer` | boots the game with the mod; what the continuous integration job drives |
| `python3 scripts/rcon_smoke.py` | asks a running server for its settings and its commands, over rcon |
| `./gradlew build` | builds the engine and the Fabric mod |
| `./gradlew :fabric:runClient` | launches a development client with the mod |

## Project layout

```
core/     the engine. No Minecraft imports are allowed here: the platform is reachable only through
          BlockStateRegistry, World, Actor and the opaque handle objects they hand out.
fabric/   the adapter. It implements those interfaces on top of Minecraft and registers commands.
docs/     generated documentation plus the reference command inventory.
scripts/  generators (command tables, documentation helpers).
```

The rule that keeps this project testable: if something needs a Minecraft type, it belongs in
`fabric/`, and `core/` gets the narrowest interface that expresses it.

## Porting a command

1. Find the upstream declaration (`@Command` in WorldEdit 7.3.17 or FastAsyncWorldEdit) and read its
   parameters, switches and permissions.
2. Implement the behaviour in the group class that matches upstream (`RegionCommands`,
   `GenerationCommands`, `BrushCommands`, `ToolCommands`, …) under
   `core/src/main/java/com/maxlananas/fawebim/core/command/`. Reuse what exists: `Operations` holds the
   shape generators and terrain algorithms, `Parsers` compiles masks/patterns/blocks,
   `EditSession` handles writes, history, limits and timeouts.
3. Register it with `registry.registerUnlessPresent(...)` so a name implemented elsewhere is never
   shadowed, and fill in the description, group, arguments and flags — the generated documentation
   and the command suggestions read those fields.
4. Run the workflow below; the command disappears from `docs/STATUS.md` when the registry no longer
   needs a stub for it.

### Aliases and sub-commands

WorldEdit declares sub-commands inside a container (`/brush rock`, `/tool farwand`, `/schem delete`)
and spells aliases with slashes (`/mirror`). Both facts are encoded in the generated tables:

* `SubCommandTable` routes a spelling to the command that implements the behaviour, so `middle`
  runs `//center` and `blob` runs `/brush rock`.
* `StubTable` holds the names that nothing implements yet. It shrinks automatically.

Both files are generated by `scripts/generate_command_tables.py` from
`docs/commands-inventory.json` (the reference declarations) and `docs/commands-spec.json` (the live
registry). Never edit them by hand; re-run the script instead.

```bash
./gradlew :core:genDocs
python3 scripts/generate_command_tables.py
./gradlew :core:selfTest
./gradlew :core:genDocs     # picks up the updated tables
python3 scripts/flag_audit.py
python3 scripts/player_audit.py
```

`scripts/flag_audit.py` is the flag gate: it compares every upstream `@Switch` and `@ArgFlag` with
what the registry declares (same name, same kind), and it checks that the brush factory actually
reads each flag the brush table declares. A flag that is accepted and then ignored is a porting bug,
so the audit exits non-zero when it finds one. When a value flag fills a parameter whose name
differs from the switch letter, the brush table spells it `parameter:letter` (`-m <sourceMask>` on
the clipboard brush), which is also how the factory finds the value.

## Configuration

`Config` declares every setting once, in a table: the key a player types in game, the path the same
value has in `config/fawebim.yml`, the type, a sentence saying what it does, and the field behind it.
Adding a setting means adding a row there; `/fawebim settings`, `/fawebim set` and the file all read
that row, so nothing has to be kept in sync by hand.

Two rules follow from that:

* A setting must change something. `python3 scripts/settings_audit.py` fails when a declared key is
  read nowhere else in the sources, and it is part of the verification list below.
* A setting must be reachable in game. The chat form is generated from the same table, and the
  settings screen draws itself from `ConfigUi`, which groups, filters and validates those rows, so a
  new setting appears in the sidebar and in the search without touching the client code.
* A behaviour the platform cannot honour does not get a knob. The mod ships no switch that only
  pretends: those are listed under *Known platform limits* in the README instead.

## Platform rules

The engine is testable because everything platform specific sits behind one interface. Keep it that
way:

* `core/` never imports `net.minecraft`. A new engine capability gets a method on `World`,
  `BlockStateRegistry` or `Actor`, with a safe default, and `fabric/FabricWorld.java` implements it.
* The mod reads the world folder, it never writes it: `World.regionDirectory()` is read-only on
  purpose. Chunk-level commands (`/anvil`) decide what qualifies from the stored chunk data and then
  edit the chunks through `World`, because rewriting a region file under a running server is how
  FAWE's own anvil commands broke worlds.
* Where a behaviour depends on the client or on an absent plugin (JavaScript engines for
  CraftScripts, PlotSquared claims for `deleteallunclaimed`, a server-side mouse wheel), implement
  what the platform allows and say the rest in the command output — a silent no-op is worse than an
  explicit message.
* A machine without the Minecraft jars can still screen the adapter for the mistakes that matter,
  such as a call to a method the engine never declared:

  ```bash
  python3 scripts/fabric_screen.py --engine core/build/classes/java/main --ecj /path/to/ecj.jar
  ```

  It compiles `fabric/` with Eclipse's batch compiler and filters out every report that is only a
  consequence of the game being absent. Anything it prints is a real defect; the Gradle build
  compiles the adapter properly and is still the source of truth.

## Verifying a change

A change is ready when all of the following hold:

1. `./gradlew :core:selfTest` passes, and `./gradlew :core:checkInventory` reports no unresolved
   WorldEdit or FAWE name. `python3 scripts/flag_audit.py` reports no missing, mistyped or unread
   WorldEdit or FAWE name. `python3 scripts/player_audit.py` reports no missing, mistyped or unread
   flag, and `python3 scripts/settings_audit.py` no configuration key that nothing reads.
2. `./gradlew build` succeeds.
3. `./gradlew :core:genDocs` shows no unexpected change in
   [`docs/STATUS.md`](docs/STATUS.md) (a ported command must move from *still to port* to
   *implemented*, nothing else).
4. New behaviour has a test in `core/src/test/java/com/maxlananas/fawebim/core/test/` when it can be
   exercised without Minecraft — shapes, masks, patterns, parsers, schematics, history and the
   command registry all can.
5. The engine stays free of Minecraft imports.

Do not claim that something works because it looks right: run it. If a change can only be verified
in game (rendering, click handling, world access), say so explicitly in the pull request.

## Style

* Java 21, four-space indentation, `camelCase`, `final` for immutable data.
* One public type per file, package names in `lowercase`.
* Prefer plain data structures and explicit code over layered abstraction; the engine is on the hot
  path of every edit.
* Keep allocations out of per-block loops: reuse arrays, avoid boxing, prefer primitive maps.
* Fail loudly for user errors (`CommandRegistry.error("...")`) and never swallow an exception
  without a comment explaining why it is safe to ignore.
* Command messages are short, in English, and use the same `§` colour codes the existing ones use.

## Submitting

1. Fork, branch from `main`, keep the changes focused on one topic.
2. Commit messages: a short imperative subject, then a body explaining *why* when it is not obvious.
3. Make sure the verification list above passes, and mention in the pull request which parts were
   tested and how (engine tests, in-game, both).
4. Open the pull request against `main` and describe the command surface change (names added,
   aliases wired, stubs removed).
